# crates/aion-reputation — Reputation Store + PoIG Reward Computation

Implements the multi-dimensional decaying reputation store from `docs/ARCHITECTURE.md` / `docs/security/THREAT-MODEL.md` and the PoIG reward formula from `docs/POIG-SPEC.md`.

**Status: real implementation, milestone 25.** `cargo test -p aion-reputation` → 19/19 passing:

- `reputation.rs` — `ReputationStore`, ported from and pinned against `simulations/poig_sim/poig_sim/reputation.py` (that Python module is the validated reference this crate must not silently diverge from). Reputation is tracked per-dimension (`completion_reliability`, `verification_reliability`), never collapsed to a single global scalar in the underlying store, and is non-transferable (no API in this module moves a dimension between identities — one test confirms two identities' records stay fully independent). A fresh identity starts at `BASELINE_SCORE` (nonzero, so a first job is possible, but well below an established worker's steady-state), grows only asymptotically toward `MAX_SCORE` with diminishing returns per successful job (never in one jump — directly enforcing the Sybil-resistance argument `simulations/poig_sim/tests/test_sybil_cluster.py` proves only indirectly through `market.py`), decays back toward baseline when idle, and is penalized (capped at a 0.5 composite penalty) by lost disputes.
- `poig.rs` — the PoIG reward formula and its `UsefulWorkScore` anti-farming gate, ported from and pinned against `simulations/poig_sim/poig_sim/poig.py`. `useful_work_score` is the load-bearing gate: zero unless the job traces to real, signed, escrow-backed demand from a requester distinct from the worker, or to network-issued benchmark provenance (which bypasses every other check, matching the Python reference's check ordering — tested explicitly). `demand_factor` clamps the escrow-to-base-value ratio at `DEMAND_FACTOR_CAP` so a single large self-funded escrow can't unboundedly amplify reward. `compute_reward` multiplies all eight PoIG factors together; tests confirm the self-dealing gate holds at zero even when every other factor is simultaneously maxed, and that a low `reputation_factor_value` scales reward down proportionally.

Honest scope note: this crate ports `reputation.py` and `poig.py` only, not `simulations/poig_sim/poig_sim/market.py`'s job-orchestration layer (job creation, escrow bookkeeping, verification-tier dispatch) — `compute_reward`'s `verification_confidence_value` and `reputation_factor_value` inputs are the caller's responsibility to source from `crates/aion-verifier`'s `tier` module and this crate's own `ReputationStore` respectively, exactly as the Python reference takes them as already-computed inputs too. Because the Python reference only exercised `reputation.py`'s decay/growth/penalty behavior indirectly (through `market.py`-orchestrated attack scenarios), this crate's `reputation.rs` tests are direct unit tests on the ported logic itself — genuinely new test coverage, not just a mechanical translation of existing Python test bodies.

One real finding surfaced while porting: repeated floating-point subtraction and `.max(BASELINE_SCORE)` clamping in the decay path can leave a fully-decayed record a few ULPs above the `BASELINE_SCORE` constant rather than bit-identical to it (e.g. `0.15000000000000002`) — an artifact of IEEE 754 arithmetic, not a logic bug. The relevant test compares with an epsilon rather than asserting exact equality, documented inline.

**Not yet done:** no orchestration layer (`market.py`'s Rust equivalent) exists yet to wire `ReputationStore` and `compute_reward` together with real job objects (`crates/aion-protocol`) and real verification-tier output (`crates/aion-verifier`) end-to-end — that wiring is the natural next step once a real job-execution pipeline exists (Phase 4). No routing-score (`routing.py`) or verification-rate (`verification.py`) port yet either; `verification.py`'s adaptive rate logic was already ported separately into `crates/aion-verifier/src/tier.rs`.
