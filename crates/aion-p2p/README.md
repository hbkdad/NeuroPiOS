# crates/aion-p2p — P2P Networking

rust-libp2p wrapper per `docs/adr/0002-p2p-stack.md`.

**Status: real implementation, milestone 16.** `cargo test -p aion-p2p` → 15/15 passing (8 unit + 7 real network integration tests):

- **GossipSub** pub/sub over real TCP+Noise+Yamux, message signing required (`ValidationMode::Strict`, `MessageAuthenticity::Signed`) — anonymous/unsigned gossip is not permitted, since every AION gossip message must be attributable to a peer for the anti-spam/reputation layers in `docs/security/THREAT-MODEL.md`. **Peer scoring is active** (`with_peer_score`, milestone 5), with an explicit, deliberately-tuned `TopicScoreParams` for the job-announcements topic (`job_announcements_topic_score_params`) — not left as unconfigured library defaults, per `docs/adr/0002-p2p-stack.md`'s requirement that every gossip topic get its own anti-spam policy. Rewards mesh tenure and first-message delivery; penalizes under-delivery and (heavily, quadratically) invalid messages. Values are a documented starting point, not yet tuned against real network data — same caveat as every other weight in this codebase (see `docs/POIG-SPEC.md`).
- **Identify**, wired in alongside GossipSub and Kademlia via a combined `AionBehaviour` (`#[derive(NetworkBehaviour)]`).
- **Kademlia**, on a custom protocol name (`/aion/kad/0.1.0`, deliberately distinct from the default `/ipfs/kad/1.0.0` so an AION node never accidentally joins or pollutes the public IPFS DHT), explicitly set to **server mode** (`kad::Mode::Server`) at construction — the library default is client mode, which silently refuses to answer other peers' FIND_NODE requests until an external address is confirmed via AutoNAT, which would make every AION node a DHT free-rider and break discovery entirely. Kademlia's own mode still isn't auto-driven by this crate's AutoNAT status (a deliberate, unchanged choice — see the AutoNAT bullet below), so this override remains necessary regardless of AutoNAT's findings. `feed_identify_into_kademlia` bridges addresses learned via Identify into Kademlia's routing table (the standard libp2p integration pattern — Kademlia does not do this automatically).
- **Identity bridging**: `keypair_from_identity` constructs a `libp2p::identity::Keypair` from the exact same Ed25519 key material as an `aion_crypto::Identity` (verified by a test that checks the raw public-key bytes match, not just that the derivation is deterministic) — a node's P2P PeerID is genuinely the same key as its `aion_crypto::Identity`, not two unrelated keys.
- **Nonzero `idle_connection_timeout`** (milestone 11, `with_swarm_config`) — see "Resolved issue" below for why this exists and what it fixes.
- `tests/gossip_roundtrip.rs` — two independent swarms, real TCP loopback connection, manual dial, one peer's published message is actually received by the other, byte-for-byte (~0.5s), with peer scoring active throughout.
- `tests/kademlia_discovery.rs` — a real Kademlia FIND_NODE request/response round-trips successfully end-to-end over `/aion/kad/0.1.0`. Honestly scoped: in this 2-node network the response legitimately comes back empty (a FIND_NODE responder returns peers from its own routing table closer than itself, and a fresh 2-node network has none yet) — what's proven is the protocol round-trip works, not that discovery finds anyone in a network this small.
- `tests/kademlia_multi_hop_discovery.rs` — the 3-node relayed case: peer C discovers peer A entirely through peer B's FIND_NODE response, without C ever dialing A directly. This is the Phase 3 MVP exit criterion "three machines discover each other," and was an open, root-caused-but-unsolved bug through milestone 10 (see "Resolved issue" below) — now real and passing.
- **Connection limits** (`connection_limits::Behaviour`, milestone 6), wired into `AionBehaviour` with explicit, documented defaults (`default_connection_limits`) covering pending/established/per-peer/total caps — `max_established_incoming` is deliberately capped independently from the other limits to prevent an eclipse attack, per the underlying behaviour's own documented recommendation. `build_swarm_with_limits` lets a caller (tests today, `aion-node`'s operator-configured resource caps later) override the defaults. `tests/connection_limits.rs` proves real enforcement: a peer configured with zero allowed inbound connections actually rejects a live dial attempt (`SwarmEvent::IncomingConnectionError`), with a control test confirming the same dial succeeds against a peer with normal limits.
- **AutoNAT** (`autonat::Behaviour`, milestone 15) — reachability DETECTION (not traversal; that's circuit relay, see below). A single `autonat::Behaviour` acts as both a client (asks a peer to dial it back, to learn whether its own address is publicly reachable) and a server (performs that dial-back for other peers) — the library's own dual-role design. `default_autonat_config` uses the production-correct `only_global_ips: true` (a private/loopback address must never count as evidence of public reachability); `build_swarm_with_limits_and_autonat_config` lets tests override that where loopback addresses are the only kind available. `tests/autonat_reachability.rs` proves the real wire protocol: peer B asks peer A to dial back, A genuinely dials B's advertised address and succeeds, and B's `nat_status()` transitions from `Unknown` to `Public(addr)` — a real request/response exchange over `/libp2p/autonat/1.0.0`, not a stubbed status flip.
- **Circuit relay** (`relay::Behaviour` + `relay::client::Behaviour`, milestone 16) — the actual NAT-traversal TRANSPORT that AutoNAT can only tell a node it needs. Every node built by this crate gets BOTH roles (relay-server, so it can help relay for others; relay-client, so it can dial an otherwise-unreachable peer through a relay) rather than treating relaying as opt-in — the same "no free-riders" choice already made for Kademlia's forced server mode. Wiring this in required a `SwarmBuilder` transport-level change (`.with_relay_client(noise::Config::new, yamux::Config::default)`), not just another `NetworkBehaviour` field, since dialing a `/p2p-circuit` address is a real transport concern, not only a protocol-level one. `tests/circuit_relay.rs` proves the real 3-node case: peer C connects to peer A entirely through relay node R — C dials only an address naming R (`R_addr/p2p/R_peer_id/p2p-circuit/p2p/A_peer_id`), a real reservation protocol exchange happens between A and R first, and the resulting C↔A connection is genuinely end-to-end authenticated (a real Noise handshake, real PeerId verification) despite A's own direct address never being part of what C dialed or knew. Verified stable across 5 repeated runs before committing.

**Not yet done (explicitly deferred, not hidden):**
- **DCUtR** (Direct Connection Upgrade through Relay — hole-punching to upgrade a relayed connection to a direct one) is not implemented; relayed connections stay relayed for their whole lifetime, which works but doesn't get the bandwidth/latency benefit of a direct path once one becomes viable.
- **`app_specific_weight`** in peer scoring is unused — reserved for `crates/aion-reputation`'s multi-dimensional reputation score to plug in once that crate exists as real Rust (currently only the Phase 2 Python simulator).
- Relay rate limits (`relay::Config::default()`'s per-peer/per-IP reservation and circuit caps) are library defaults, not yet tuned against real network load — same caveat as every other default in this crate.

## Resolved issue: 3-node relayed Kademlia discovery (milestone 4 → milestone 11)

Milestones 4 and 9 documented this as an open, root-caused-but-unsolved bug: C's `get_closest_peers(A)` query via B always completed with an empty peer list and `stats: { requests: 1, success: 0, failure: 1 }`, even though B genuinely computed the correct response (`kad::Event::InboundRequest { request: FindNode { num_closer_peers: 1 } }` proved B's routing-table lookup for A succeeded).

Milestone 11 resolved it using `RUST_LOG=libp2p_kad=trace,libp2p_swarm=debug` protocol-level tracing (the next step both prior write-ups called for, since source-reading alone had been exhausted). The trace showed the real sequence: B computes and queues the FIND_NODE response for C, but the underlying B↔C TCP connection is then torn down via `SwarmEvent`'s `KeepAliveTimeout` roughly 90ms later — before C ever receives the response — and the query fails.

Root cause: `libp2p_swarm::Config`'s `idle_connection_timeout` defaults to `Duration::ZERO`. The instant every behaviour handler on a connection reports no further pending work, the swarm closes it with **no grace period**. For a request/response protocol like Kademlia, the *responder* side can report "no more work" as soon as it queues its reply — which races the reply actually being flushed to the socket. On the small, fast loopback connections in this test suite, that race is lost essentially every time.

**Fix** (`crates/aion-p2p/src/lib.rs`, `build_swarm_with_limits`): `.with_swarm_config(|cfg| cfg.with_idle_connection_timeout(Duration::from_secs(30)))`. A nonzero grace period gives an in-flight protocol response time to actually leave the socket before an idle connection is reclaimed. Verified fixed by re-running the same tracing setup after the change (`success: 2, failure: 0`, C's routing table now genuinely contains A) and by 5 repeated clean runs of the new `tests/kademlia_multi_hop_discovery.rs` to rule out a fluke.
