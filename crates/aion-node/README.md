# crates/aion-node — Node Runtime

Node identity, hardware auto-detection, Node Safety resource caps, and composable node-role flags, per `docs/ARCHITECTURE.md`.

**Status: real implementation, milestone 31.** `cargo test -p aion-node` → 32/32 passing:

- `hardware.rs` — real hardware detection via the `sysinfo` crate (OS, hostname, CPU core count, total memory/swap), tested against the actual values in whatever container/host runs the tests — not mocked. GPU/VRAM detection is explicitly deferred (no portable dependency-light way to enumerate CUDA/ROCm/Metal GPUs, and no GPU exists in this dev container to test against — see `docs/research/CAPABILITY-MATRIX.md`), not stubbed with fake values.
- `resource_caps.rs` — the Node Safety enforcement point: `ResourceCaps::locked_down()` is the mandatory default (a fresh node accepts *no* work until the operator explicitly widens its caps), plus CPU/memory/working-hours checks, including a working-hours window that correctly wraps past midnight. **`ResourceCaps::to_connection_limits()`** (milestone 17) closes the "bandwidth cap and P2P connection limits are two independent, unconnected knobs" gap `crates/aion-p2p/README.md` used to flag: connection caps scale with `max_bandwidth_mbps` under a documented, conservative Mbps-per-connection assumption, clamped to never exceed `aion_p2p`'s own defaults. Deliberately does NOT zero out connectivity even at `locked_down()`'s `max_bandwidth_mbps: Some(0)` — "no job-payload bandwidth budgeted yet" is not the same claim as "this node should be unreachable"; baseline protocol traffic (gossip, Kademlia, Identify) isn't job execution, so a resource-locked node still gets a minimal (floored at 1) connection allowance rather than being cut off from the network entirely.
- `roles.rs` — composable node-role flags (`Compute`, `Inference`, `Training`, `Storage`, `Validator`, `Benchmark`, `Gateway`); a single node can hold any combination.
- `lib.rs` — `Node::bootstrap()` ties these together with a real `aion_crypto::Identity` (fresh Ed25519 keypair per node). `Node::build_swarm()` builds an `aion-p2p` swarm from the node's own identity (bridged via `aion_p2p::keypair_from_identity`) and derives its connection limits from the node's own `caps`, rather than an unrelated fixed default. `tests/node_gossip.rs` proves two `Node`s gossip a message to each other end-to-end via the raw (manually-driven) swarm, and that the swarm's on-wire PeerID genuinely corresponds to the node's `aion_crypto::Identity` public key, not a separately-generated one. `tests/resource_caps_connection_limits.rs` proves the derived connection cap is genuinely ENFORCED by the real swarm, not just correct in isolation.
- `handle.rs` (milestone 18, extended milestones 19-24) — **`Node::spawn()`** hands a node's swarm off to a background `tokio` task that owns and drives it, returning a `NodeHandle`: a channel-based command/event API (`listen_on`, `dial`, `subscribe`, `publish`, `add_kademlia_bootstrap_peer`, `find_closest_peers`, `add_external_address`, `next_event`) so a caller never touches `Swarm` directly. Honestly scoped: covers what `tests/node_gossip.rs` and `aion-p2p`'s own `kademlia_discovery.rs`/`autonat_reachability.rs`/`circuit_relay.rs`/`dcutr_hole_punch.rs` already proved work manually (gossip, connectivity, Kademlia, AutoNAT status, relay-server AND relay-client activity, DCUtR hole-punch outcomes) — meant to grow incrementally as real callers need more of the surface, not built out speculatively ahead of any actual need. `tests/handle_gossip.rs`, `tests/handle_kademlia.rs`, `tests/handle_autonat.rs`, and `tests/handle_relay.rs` cover gossip, Kademlia discovery, AutoNAT, and relay-server activity respectively. `tests/handle_dcutr.rs` extends `handle_relay.rs`'s exact 3-node topology and proves a real DCUtR direct-connection upgrade surfaces as `NodeEvent::DirectConnectionUpgrade`. `tests/handle_relay_client.rs` (milestone 24) proves the complementary CLIENT-side confirmations on the SAME topology: the reserving peer (A) sees `RelayClientReservationAccepted` and `RelayClientInboundCircuitEstablished`, and the dialing peer (C) sees `RelayClientOutboundCircuitEstablished` — each side of a relayed connection genuinely observing its own milestone, not just that the connection succeeds. The by-now-familiar connection-limit interaction from milestones 20-22 recurred here too and was fixed and documented the same way. All handle tests honestly scoped the same way their lower-level `aion-p2p` counterparts are, and verified stable across 5 repeated runs before committing.
- `capped_storage.rs` (milestone 31) — **`CappedContentStore`** gates `aion_storage::ContentStore` usage through `ResourceCaps::max_storage_mb`, closing the same class of gap `to_connection_limits()` already closed for P2P connection limits: a node's storage cap and its actual `ContentStore` disk usage used to be two independent, unconnected knobs. `put` measures current usage authoritatively via `ContentStore::disk_usage_bytes()` (a real filesystem sum, not a separately-tracked counter that could drift) and rejects outright — no partial write — anything that would push total usage over the cap; `get` is never gated, matching `allows_new_work`'s existing principle that caps constrain accepting new resource commitment, not access to what's already stored. At `ResourceCaps::locked_down()`'s default (`max_storage_mb: 0`), every `put` is rejected, the same "accept no new work until the operator explicitly widens the cap" behavior `allows_new_work` already enforces for CPU/memory. One test proves the cap is enforced cumulatively across multiple puts, not just per-call (two puts that individually fit can still combine to exceed the cap).

**Not yet done:** the `aion-runtime`/`aion-verifier`/`aion-reputation` dependencies listed in the original plan (those crates don't exist yet as `aion-node` dependencies, apart from `aion-storage` now wired in via `capped_storage.rs`); `NodeHandle`'s command surface now covers every major `aion-p2p` behaviour used across this crate's tests — further growth is expected only as new real callers need more of the surface, per the module doc's "grow incrementally" scope note. `CappedContentStore` isn't yet wired into `NodeHandle`/the P2P layer (no P2P-served content requests exist yet, since `aion-storage`'s network-distribution half doesn't exist either).
