# crates/aion-node — Node Runtime

Node identity, hardware auto-detection, Node Safety resource caps, and composable node-role flags, per `docs/ARCHITECTURE.md`.

**Status: real implementation, milestone 21.** `cargo test -p aion-node` → 25/25 passing:

- `hardware.rs` — real hardware detection via the `sysinfo` crate (OS, hostname, CPU core count, total memory/swap), tested against the actual values in whatever container/host runs the tests — not mocked. GPU/VRAM detection is explicitly deferred (no portable dependency-light way to enumerate CUDA/ROCm/Metal GPUs, and no GPU exists in this dev container to test against — see `docs/research/CAPABILITY-MATRIX.md`), not stubbed with fake values.
- `resource_caps.rs` — the Node Safety enforcement point: `ResourceCaps::locked_down()` is the mandatory default (a fresh node accepts *no* work until the operator explicitly widens its caps), plus CPU/memory/working-hours checks, including a working-hours window that correctly wraps past midnight. **`ResourceCaps::to_connection_limits()`** (milestone 17) closes the "bandwidth cap and P2P connection limits are two independent, unconnected knobs" gap `crates/aion-p2p/README.md` used to flag: connection caps scale with `max_bandwidth_mbps` under a documented, conservative Mbps-per-connection assumption, clamped to never exceed `aion_p2p`'s own defaults. Deliberately does NOT zero out connectivity even at `locked_down()`'s `max_bandwidth_mbps: Some(0)` — "no job-payload bandwidth budgeted yet" is not the same claim as "this node should be unreachable"; baseline protocol traffic (gossip, Kademlia, Identify) isn't job execution, so a resource-locked node still gets a minimal (floored at 1) connection allowance rather than being cut off from the network entirely.
- `roles.rs` — composable node-role flags (`Compute`, `Inference`, `Training`, `Storage`, `Validator`, `Benchmark`, `Gateway`); a single node can hold any combination.
- `lib.rs` — `Node::bootstrap()` ties these together with a real `aion_crypto::Identity` (fresh Ed25519 keypair per node). `Node::build_swarm()` builds an `aion-p2p` swarm from the node's own identity (bridged via `aion_p2p::keypair_from_identity`) and derives its connection limits from the node's own `caps`, rather than an unrelated fixed default. `tests/node_gossip.rs` proves two `Node`s gossip a message to each other end-to-end via the raw (manually-driven) swarm, and that the swarm's on-wire PeerID genuinely corresponds to the node's `aion_crypto::Identity` public key, not a separately-generated one. `tests/resource_caps_connection_limits.rs` proves the derived connection cap is genuinely ENFORCED by the real swarm, not just correct in isolation.
- `handle.rs` (milestone 18, extended milestones 19-21) — **`Node::spawn()`** hands a node's swarm off to a background `tokio` task that owns and drives it, returning a `NodeHandle`: a channel-based command/event API (`listen_on`, `dial`, `subscribe`, `publish`, `add_kademlia_bootstrap_peer`, `find_closest_peers`, `add_external_address`, `next_event`) so a caller never touches `Swarm` directly. Honestly scoped: covers what `tests/node_gossip.rs` and `aion-p2p`'s own `kademlia_discovery.rs`/`autonat_reachability.rs`/`circuit_relay.rs` already proved work manually (gossip, connectivity, Kademlia, AutoNAT status, relay-SERVER activity), not a full command surface over every behaviour this crate wires in — relay-CLIENT reservation confirmation isn't its own event yet, though `listen_on`/`dial` already work transparently with `/p2p-circuit` addresses via the generic commands — meant to grow incrementally as real callers need more of the surface, not built out speculatively ahead of any actual need. `tests/handle_gossip.rs`, `tests/handle_kademlia.rs`, and `tests/handle_autonat.rs` cover gossip, Kademlia discovery, and AutoNAT respectively. `tests/handle_relay.rs` (milestone 21) proves a real 3-node relay scenario end-to-end through the handle API: node R relays for node A, node C connects to A entirely through R without ever dialing A directly, and R's own handle genuinely reports both `RelayReservationAccepted` (A's reservation) and `RelayCircuitAccepted` (C's relayed connection) as real events — not just that the end-to-end connection succeeds. Milestone 20's `max_established_per_peer` connection-limit finding recurred here in a new shape (R needs `max_established_incoming` room for BOTH A and C simultaneously) and was fixed and documented the same way: real, not papered over. All handle tests honestly scoped the same way their lower-level `aion-p2p` counterparts are, and verified stable across 5 repeated runs before committing.

**Not yet done:** the `aion-runtime`/`aion-verifier`/`aion-storage`/`aion-reputation` dependencies listed in the original plan (those crates don't exist yet, apart from `aion-verifier` which now exists separately and isn't wired into `aion-node`); `NodeHandle`'s command surface is intentionally partial (see `handle.rs`'s scope note above) — relay-client reservation confirmation isn't its own event yet, only what real gossip/connectivity/discovery/reachability/relay use cases have needed so far.
