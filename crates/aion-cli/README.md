# crates/aion-cli — `aion` CLI

Target UX: `aion devnet up|status|down|logs` (local multi-node dev network per the orchestration brief), plus node/job/model management subcommands.

**Status: real implementation (devnet only), milestone 33.** `cargo test -p aion-cli` → 17/17 passing:

- `devnet.rs` — coordination logic for a **real multi-process** local devnet, built entirely on the filesystem (no IPC socket, no shared memory): `up` spawns one genuine OS child process per node (this same binary, re-invoked in a hidden `worker` subcommand); each worker writes a small plain-text record (`pid`, `peer_id`, `listen_addr`, `connected_peers`) to `node-<index>.info` in a shared directory. Node 0 is always the bootstrap peer. `status` re-derives every node's liveness via `kill -0` (never trusted from the record alone -- a crashed worker still leaves its last record behind) and reports its last-known connections. `down` sends every live node SIGTERM and clears the directory. `up` refuses to run again over an already-live devnet, so a caller can't accidentally leak orphaned processes by forgetting to `down` first. `read_log_from(dir, index, from_byte)` (milestone 33) returns whatever's been appended to a node's log since a byte offset — calling it again with the previous call's returned length as the next `from_byte` is a real, working `tail -f`, which `logs --follow` is just a sleep loop around.
- `worker.rs` — the actual per-process node logic: bootstraps a real `aion_node::Node` with widened caps (the same `max_bandwidth_mbps: Some(10)` pattern every multi-node P2P/handle test in this workspace already uses), listens on an OS-assigned loopback port, writes its own record once ready, and — if it isn't node 0 — polls (bounded, 30s timeout, not an infinite wait) for node 0's record and dials it. Every real `ConnectionEstablished` event updates the worker's own record's `connected_peers` line, so `status` reports genuine P2P connectivity, not just "the process is alive." Also now prints real log lines (listening address, bootstrap dial, each new connection) — added in milestone 33 specifically so `logs` would have real content to show; before that, a worker's log file was silently empty on the happy path.
- `main.rs`'s `devnet logs <index> [--follow]` subcommand (milestone 33) prints a node's log file (`node-<index>.log`, written there by `up`'s stdout/stderr redirection) and, with `--follow`, keeps polling and printing new output every 300ms until interrupted — a real `tail -f` for a devnet node an operator is debugging.
- `tests/devnet_e2e.rs` — **the first genuinely multi-process tests in this entire workspace.** Every other multi-node P2P test so far (in `crates/aion-p2p` and `crates/aion-node`) spawns multiple `Node`s as `tokio` tasks within one test process; these tests actually invoke the compiled `aion` binary (`env!("CARGO_BIN_EXE_aion")`) as separate real OS processes via `devnet up`, polling `status`/`logs` until real cross-process behavior is observed: two nodes connecting to each other, `down` actually terminating them, a live devnet refusing a second concurrent `up`, and (milestone 33) `logs` showing a real running worker's actual "listening on ..." output. Verified stable across 5 repeated runs before committing.

**A real bug found and fixed while building this** (documented, not hidden): worker child processes inherit their parent's stdout/stderr by default. Since a `devnet up` invocation exits almost immediately after spawning workers that then run indefinitely, anything piping `up`'s own output (a test harness's `Command::output()`, a shell capturing `$(aion devnet up ...)`) would block forever waiting for EOF on a pipe the still-running workers keep open. Fixed by redirecting each worker's stdout/stderr to its own `node-<index>.log` file instead of inheriting -- a genuine improvement for real devnet usage (per-node logs an operator can `tail -f`), not just a workaround for the test hang that surfaced it. Milestone 33's `logs` subcommand is what actually makes those log files useful to a human, not just a bug-fix side effect.

Honestly scoped: `devnet up|status|down|logs` only. No node/job/model management subcommands yet (those need a real job-execution/settlement pipeline, Phase 4/10, which doesn't exist). No process supervision beyond spawn/kill (a crashed worker just stops reporting connections in `status`; nothing auto-restarts it). No log rotation/truncation handling in `logs` beyond reporting the current length when nothing new exists. `.aion-devnet/` (the default runtime directory) is gitignored.
