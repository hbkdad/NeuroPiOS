# AI Verification Matrix

Scoped to methods relevant to verifying that claimed AI compute work was actually performed, and performed correctly, at a given verification level (see `docs/VERIFICATION.md` for how levels map to job types).

| Method | Security assumption | Proving cost | Verification cost | Latency added | GPU compatibility | Privacy | Model-size limits | Production maturity (2026) | Recommended usage |
|---|---|---|---|---|---|---|---|---|---|
| Commitment/hash of I/O | Prover cannot equivocate after commit; no correctness guarantee | ~0 | ~0 | None | Any | Full (commit can be hash-only) | None | Mature | L1: pairs with random spot-replication; alone only for L0/dev jobs |
| Redundant/replicated execution (N-of-M re-run) | Majority of replicas honest; workload is deterministic-enough for agreement within tolerance | N× the base job cost | O(N) comparisons | Low if parallel | Any | Low (N nodes see the input) | None | Mature (used by Akash-adjacent and Bittensor-style networks, though not for correctness there) | L2: general inference/training jobs where a numeric-tolerance comparison is meaningful |
| Deterministic/reproducible execution (fixed seed, fixed kernel path, containerized env) | Hardware/driver/kernel stack is pinned tightly enough that outputs are bit- or tolerance-exact | ~1× (no extra compute, just constrained env) | Cheap (single re-run + diff) | Low | Narrow — requires pinning GPU vendor/driver/kernel fusion path, breaks portability | Low | None | Partially mature; genuinely hard across heterogeneous GPU fleets (float non-associativity) | L3: high-value jobs where the requester can accept restricted hardware pools |
| Optimistic commit + dispute window + bisection (Gensyn Verde/REE pattern) | Honest-minority assumption during the challenge window; bisection game correctly isolates the disputed computation step | ~1× in the common (no dispute) case; O(log n) re-execution steps only if disputed | Cheap unless disputed | Dispute window (minutes–hours) | Any | Medium | None inherent | Emerging (Gensyn testnet-stage as of 2026; not yet mainnet-proven at scale) | L4: default "challenge protocol" tier — cheap by default, only pays arbitration cost under real dispute |
| TEE-based attestation (SGX/SEV/TDX/Nitro) | Hardware enclave + attestation chain of trust is not compromised; no side-channel extraction | ~1x + attestation overhead | Attestation-signature check, cheap | Low | Requires enclave-capable hardware; excludes most consumer GPUs today | High (input stays inside enclave) | None inherent | Mature as a primitive, narrow in decentralized-GPU-fleet coverage | Optional privacy-preserving path for confidential jobs (see `docs/PRIVACY` classification), not a universal verification default because it narrows the eligible hardware pool |
| ZKML (EZKL/circuit-based proof of correct inference) | Soundness of the underlying SNARK/STARK construction; circuit correctly encodes the model | Very high, scales badly with model size (sub-second for MNIST-scale ONNX ≤~50M params; full LLM inference impractical as of 2026) | Cheap (proof verification, e.g. on-chain) | High (proving time can dominate) | Poor — CPU-bound proving, not GPU-accelerated in most current tooling | High (can prove correctness without revealing weights or inputs) | Small models only (~≤50M params practical in 2026) | Early — real but narrow (image classification, small MLPs); not viable for LLM-scale inference | L5: narrow proof-of-concept only (Phase 11), for small models or small sub-components (e.g., proving a quantization step), not general-purpose |
| Multi-validator quorum (weighted, adaptive rate) | Enough independent validators are honest and not colluding; quorum size scales with job value | N-validator cost, N scaled to job value | O(N) | Depends on quorum coordination | Any | Low–Medium | None | Mature (used across Bittensor/Allora in different forms) | L6: high-value/high-risk jobs; combine with L2/L4 rather than replace them |

## Notes
- No single method covers all workloads — this is why `docs/VERIFICATION.md` defines tiers (L0–L6) rather than one mechanism.
- ZKML and TEE both currently trade away either cost, GPU compatibility, or hardware-pool breadth in exchange for stronger cryptographic/hardware guarantees; neither is a drop-in replacement for the cheaper statistical/dispute-based methods at AION's expected job volumes in early phases.
- "Proving cost" and "production maturity" figures are sourced from 2026 research (EZKL benchmarks, Bionetta, NANOZK — see `RESEARCH-LOG.md` 2026-07-28 entry) and should be re-verified before Phase 11 begins, since zkML tooling is moving quickly.
