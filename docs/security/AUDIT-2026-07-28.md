# AION Security/Supply-Chain Audit — 2026-07-28

An internal, self-run audit (not an external/independent audit — see `SECURITY.md` and `docs/ROADMAP.md` Phase 13, which correctly remains "Not started" for that reason). This document records what was actually checked and what it actually found, per `AGENTS.md`'s rule against claiming "audited"/"secure" without shown output.

## Scope and method

Checked, with real commands and real output (not assumed):
- `cargo audit` (installed fresh via `cargo install cargo-audit --locked`, run against the workspace `Cargo.lock`).
- `pip-audit` (installed fresh in `simulations/poig_sim`'s venv).
- `grep` for `unsafe` blocks across all real Rust crates.
- A prod-code-path-vs-test-module split of every `.unwrap()`/`.expect()`/`panic!()` occurrence across all real Rust crates.
- `grep` for hardcoded secrets/keys/passwords across `crates/` and `simulations/`.
- `cargo tree -i <crate>` to trace each flagged dependency back to its actual dependency path.
- `cargo update --dry-run` to check whether any flagged dependency has an in-range fix available.
- Presence/absence of `.github/workflows/`, `.github/dependabot.yml`, and CI check runs on PR #1 (`get_check_runs` returned zero).

## Findings

### 1. Dependency vulnerabilities — real, all transitive through libp2p

`cargo audit` against the workspace `Cargo.lock` (378 crates scanned) reported:

| Crate | Version | Advisory | Issue |
|---|---|---|---|
| `hickory-proto` | 0.24.4 | RUSTSEC-2026-0119 | O(n²) CPU exhaustion during message encoding |
| `ring` | 0.16.20 | RUSTSEC-2025-0009 | AES functions may panic with overflow checking enabled |
| `rustls-webpki` | 0.101.7 | RUSTSEC-2026-0099, -0104, -0098 | Certificate name-constraint / CRL parsing issues |
| `instant` | 0.1.13 | RUSTSEC-2024-0384 | Unmaintained |
| `paste` | 1.0.15 | RUSTSEC-2024-0436 | Unmaintained |
| `ring` | 0.16.20 | RUSTSEC-2025-0010 | Unmaintained (pre-0.17) |
| `lru` | 0.11.1, 0.12.5 | RUSTSEC-2026-0002 | Unsound `IterMut` (Stacked Borrows violation) |

`cargo tree -i` confirmed every one of these is pulled in transitively through `libp2p 0.53.2`'s own dependency tree (via `libp2p-dns`, `libp2p-quic`, `libp2p-tcp`/`netlink-packet-core`, etc.) — none is a direct dependency this project chose. `cargo update --dry-run` confirmed none has an in-range fix available within `libp2p` 0.53's own version constraints. The real remediation is upgrading `libp2p` 0.53 → 0.56 (latest as of this audit), which is a breaking-change engineering task (tracked as the next milestone after this one, not yet done as of this document).

### 2. `simulations/poig_sim` has no runtime supply-chain exposure

`poig_sim` has zero third-party runtime dependencies (pure standard library; `pytest` is a dev-only dependency). `pip-audit` findings were limited to the local dev venv's `pip`/`setuptools` tooling versions, not anything the package ships or depends on at runtime.

### 3. No `unsafe` Rust anywhere in AION's own crates

`grep -rn "unsafe" crates/*/src` returned zero matches across `aion-crypto`, `aion-node`, `aion-p2p`, `aion-protocol`, `aion-reputation`, `aion-verifier`.

### 4. No unguarded panics in production code paths

Every `.unwrap()`/`.expect()`/`panic!()` in the codebase is either inside a `#[cfg(test)]` module, or (the one exception, `crates/aion-verifier/src/quorum.rs:104`) directly guarded by an `all_committed()` check on the preceding line, with a comment (`"all_committed checked above"`) documenting why it's unreachable in practice. No crash-as-DoS vector was found.

### 5. No hardcoded secrets

`grep` for API keys/secrets/passwords/private-key patterns across `crates/` and `simulations/` turned up only legitimate handling of cryptographic secret material — e.g. `aion-crypto::Identity::to_bytes` (a narrowly-scoped, documented secret-seed export) and `poig_sim`'s simulated actor secrets (`Signer.secret`, explicitly `repr=False` so it never appears in reprs/logs). Nothing resembling a leaked or committed real credential.

### 6. No CI at all (the biggest process gap)

`.github/` contained no `workflows/` directory and no `dependabot.yml` before this audit. `pull_request_read(method="get_check_runs")` against PR #1 returned `total_count: 0`. Every "tests pass" / "clippy clean" claim made in this repo's commit history up to this point was manually run and reported honestly (consistent with `AGENTS.md`'s rule against fabricated claims) — but there was no automated safety net catching a future regression.

**Remediated in this same milestone**: `.github/workflows/ci.yml` (fmt/clippy/test on Rust, pytest on Python, on every push and PR against `main`), `.github/workflows/security-audit.yml` (`cargo audit` + `pip-audit`, currently `continue-on-error: true` since finding #1 above is a known, already-tracked, not-yet-fixed issue — remove that flag once the libp2p bump lands so a *new* advisory genuinely fails CI), `.github/dependabot.yml` (weekly updates for `cargo`, `pip` in `simulations/poig_sim`, and `github-actions`).

### 7. SBOM generation still not implemented

Unchanged from `SECURITY.md`'s existing honest disclosure: no SBOM generation exists yet. Tracked as a follow-up, not fixed in this milestone.

## What this audit is NOT

Not an external/independent security review, not a smart-contract audit (no contracts exist yet — Phase 10), not a SOC 2 assessment (see the discussion below), not a penetration test. `docs/ROADMAP.md` Phase 13 remains correctly "Not started."

## On SOC 2 specifically

SOC 2 evaluates a live service organization's operational controls against real customer data over an observation period. AION has no deployed network, no live users, and no customer data yet — there is no operational control surface for an auditor to test, so pursuing SOC 2 now would be pure overhead. It is also arguably the wrong framework for a decentralized protocol: the analogous third-party assurance AION actually needs is an independent **smart-contract audit** before any mainnet/testnet deployment (already planned per `docs/adr/0001-settlement-layer.md` / `docs/adr/0004-token-development-staging.md`), plus the supply-chain hygiene this document addresses. SOC 2 would only become relevant if a centralized hosted component (e.g. a hosted dashboard/node-management control plane) is built on top of the decentralized network and handles real user data — a business/product decision, not a currently-open engineering gap.

## Update (milestone 27, same day): libp2p 0.53 → 0.56 upgrade results

Bumped `libp2p` in `crates/aion-p2p` and `crates/aion-node` from `0.53` to `0.56` (latest). Two real API breaks surfaced and were fixed (not papered over):
- `kad::Config::set_protocol_names` was removed; the replacement is `kad::Config::new(protocol_name)`, which takes the protocol name directly at construction instead of being set after the fact on a `default()` config. Fixed in `crates/aion-p2p/src/lib.rs::build_kademlia`.
- `kad::GetClosestPeersOk::peers` changed from `Vec<PeerId>` to `Vec<PeerInfo>` (`PeerInfo { peer_id, addrs }`) — libp2p 0.56 now returns each peer's known addresses alongside its ID. `NodeEvent::ClosestPeersFound`'s existing contract (`Vec<PeerId>`) didn't need to change, so both call sites (`crates/aion-node/src/handle.rs` and `crates/aion-p2p/tests/kademlia_multi_hop_discovery.rs`) now map `PeerInfo -> PeerInfo::peer_id`.

After both fixes: `cargo build --workspace --all-targets` clean, `cargo fmt --all -- --check` clean, `cargo clippy --workspace --all-targets -- -D warnings` clean, and all 129 Rust tests pass on first run. Every timing-sensitive multi-node P2P/handle integration test (`autonat_reachability`, `circuit_relay`, `dcutr_hole_punch`, `kademlia_multi_hop_discovery`, `kademlia_discovery`, `gossip_roundtrip`, `connection_limits`, `handle_gossip`, `handle_kademlia`, `handle_autonat`, `handle_relay`, `handle_dcutr`, `handle_relay_client`, `node_gossip`, `resource_caps_connection_limits`) was individually re-run 5 times and stayed stable every time — the same discipline used for every P2P test added earlier this session, applied here to re-verify a dependency bump didn't introduce hidden timing regressions even though it compiled clean.

Re-running `cargo audit` after the bump: **3 of 5 original findings are cleared** (`ring`, `rustls-webpki`, `instant`, `lru` all transitively bumped to fixed/maintained versions). **2 residuals remain, genuinely not fixable from this project's side right now:**
- `hickory-proto` 0.25.2 still carries RUSTSEC-2026-0119 (the fix is `>=0.26.1`), and a *new* one showed up in the newer version: RUSTSEC-2026-0118, which upstream marks "No fixed upgrade is available!" yet. Confirmed via `cargo update -p hickory-proto --precise 0.26.1` that the fix version isn't reachable: `libp2p-mdns 0.48.0` (pulled in by `libp2p 0.56.0`) pins `hickory-proto = "^0.25.2"`, so nothing in our own `Cargo.toml` can select a newer one without libp2p itself bumping that constraint.
- `paste` 1.0.15 remains unmaintained (RUSTSEC-2024-0436), still pinned transitively via `netlink-packet-core` (used by `if-watch`/`libp2p-tcp`).

Both are tracked, not hidden, and `security-audit.yml`'s `cargo-audit` job keeps `continue-on-error: true` for exactly this reason — these two are real, known, and currently unfixable by a version bump on our side; revisit when a future `libp2p` release loosens the `hickory-proto` constraint or ships without `netlink-packet-core`'s `paste` dependency.

Also fixed two CI bugs this same milestone, both found by watching the *first real run* of the CI added in the earlier part of this audit fail on this repository's actual PR:
- `pytest` was never installed in the `python` CI job — `simulations/poig_sim/pyproject.toml` had no dev-dependency declaration at all, so `pip install -e .` alone never pulled it in (it only worked locally because this dev container already had `pytest` installed from prior sessions). Fixed by adding a real `[project.optional-dependencies] dev = ["pytest"]` group and installing via `pip install -e ".[dev]"` in both CI workflows. Verified the fix in a genuinely fresh `venv` (not just locally), confirming 37/37 tests pass with no pre-existing `pytest` installation.
- `ci.yml`'s `push: branches: ["**"]` combined with `pull_request: branches: [main]` double-triggered every job on a feature-branch push (both events fire for the same commit on an open PR), visible as duplicate check runs in the PR's checks tab. Fixed by restricting `push` to `branches: [main]` only — feature-branch commits on an open PR are already covered by the `pull_request` (synchronize) event.
